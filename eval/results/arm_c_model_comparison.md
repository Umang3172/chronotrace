# Arm C across two local models

Arm C only, re-run against a larger model with **everything else held constant**:
the same recorded traces, the same diagnoses, the same system and user prompts
(verified byte-identical), the same temperature, seed, token cap and attempt
budget. The model is the only variable.

## Hypothesis

`RELAX_ASSERTION` on all six races was an 8B pattern-selection limit rather than
a system failure.

## Result: not supported

The larger model does not pick correctly either. It picks a **different wrong
answer**, and produces no patch for the same reason.

| R03 | `RELAX_ASSERTION` | `asyncio.Event` | `NO_REPAIR` | `none` |

Ground truth for R01–R06 is `INJECT_ASYNC_EVENT`. Neither model chose it once.

## What the 14B model said

Its R01 rationale, verbatim, alongside a `NO_REPAIR` transformation:

> The assertion over-constrains legitimate concurrency. The test should be
> relaxed to allow for the possibility that the read operation may occur before
> the write operation completes.

The rationale argues for relaxing the assertion; the transformation field says
no repair. The two disagree, and the language tracks the closing paragraph of
the system prompt almost word for word.

Both models converge on the two transformations that mean *do not patch*, from
opposite directions — 8B picked `RELAX_ASSERTION` six times, 14B picked
`NO_REPAIR` six times. The system prompt lists five transformations and spends
its last paragraph on those two. That is the most likely lever, and it was
**not** pulled: no prompt, rule or benchmark case was changed for this run.

## What this establishes, and what it does not

**Establishes.** Arm C's 0/6 is not an 8B artifact. Two local models, one nearly
twice the size and code-tuned, both emit schema-valid intents and both choose a
non-repairing transformation on every genuine read-after-write race. The
constraint layer behaves correctly throughout: valid JSON in, no patch out, no
band-aids, no false repairs, and correct abstention with the right reason on all
five controls in both runs.

**Does not establish.** That a frontier model would fail the same way. Two
quantised local models is not a trend, and the shared failure mode points at a
prompt that both may be reading the same way rather than at an inherent limit.
The Bedrock run is what settles it.

**The open risk.** ChronoTrace has never been observed making a correct repair
decision with a real model. Every successful demo to date replays a fixture
generated by the deterministic reference policy in `chronotrace/providers/local.py`,
not by a model. Until a model produces `INJECT_ASYNC_EVENT` on R01 unaided, the
end-to-end claim rests on that policy.
